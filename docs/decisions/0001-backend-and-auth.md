# 0001. バックエンドに Supabase を採用し、生徒は ID + 4桁パスワードでログインする

- **日付**: 2026-09-19
- **ステータス**: 承認

## 背景

記録を50名分・年単位で蓄積する必要があり、サーバー側の仕組みが要る。
一方で開発するのは教室の生徒3〜5名でスキルはばらばら。
教室は CoreServer（PHP + MySQL）を契約済みで、これを使う選択肢もあった。

また生徒にメールアドレスは配られておらず、
一般的なメール認証がそのままでは成立しない状況だった。

## 決定

1. バックエンドは **Supabase**（PostgreSQL + Auth）を使う
2. ホスティングは **Cloudflare Pages**。CoreServer は使わない
3. 生徒は **ID + 4桁パスワード**でログインする。先生はメール + 通常パスワード
4. 生徒アカウントは `<生徒ID>@typingsuite.invalid` のダミーメールで Supabase Auth に登録する

## 理由

**Supabase を選んだ理由**

- 言語が TypeScript に統一される。CoreServer を使うとバックエンドが PHP になり
  2言語になる。スキルがばらばらで途中参加も想定するため、言語は1つに保ちたい
- 認証を自前実装せずに済む。小中学生の記録を預かるためリスクを負いたくない
- 生徒が作る主役（練習モード・ゲーム）に時間を回せる

**CoreServer + MySQL を却下した理由**

この案の利点は「データを自分たちの管理下に置ける」ことだった。
しかし定期バックアップ（エクスポート機能）で無料枠リスクを吸収する方針が決まり、
利点が薄れた。言語が2つになる代償のほうが大きいと判断した。

**ID + 4桁パスワードにした理由**

- 生徒にメールアドレスがないため、メール認証は選べない
- 「名前を選ぶだけ」も検討したが、記録は生徒ごとの資産であり、
  持ち主が曖昧になる作りは避けたい（自分の推移を見比べられることが成功条件のため）
- 4桁は強度が低いが、守る対象が教室内の練習記録であり、
  先生がいつでもリセットできるため運用で埋め合わせがきく

## 却下した選択肢

| 選択肢 | 却下理由 |
|--------|----------|
| CoreServer + PHP で API を自作 | 言語が2つになり途中参加のハードルが上がる。認証の自前実装はリスクが重い |
| Node.js API を CoreServer に置く | CoreServer は Node.js 標準非対応。nvm 導入は自己責任で運用が不安定 |
| 生徒もメールアドレスでログイン | 教室が生徒にメールアドレスを配っていないため成立しない |
| 名前を選ぶだけ（パスワードなし） | 他人の名前を押す事故が起き、記録の持ち主が曖昧になる |
| CoreServer で静的配信 | FTP の手動アップロードが毎回発生する。複数人開発では事故のもと。契約済みであることは判断材料にしない（サンクコスト） |

## 影響

- 記録データは外部サービス上に置かれる。**定期バックアップの運用が前提**になる
- Supabase 無料枠の一時停止に備え、長期休暇明けは事前の動作確認が必要
- 先生に「アカウント発行・パスワードリセット」の運用が発生する。管理画面に機能が要る
- 後戻りする場合：DB は PostgreSQL のままセルフホストへ移せるが、
  Auth は代替の実装が必要になり、移行コストは大きい
