プロジェクト開始時のヒアリングを行う。`docs/concept.md` がまだ無い状態で使う。

## 進め方の原則

- 一度に全部聞かず、**1〜2個ずつ**質問する
- 回答を受けたら「理解した内容の要約」を示し、認識ずれがないか確認してから次へ進む
- 不明確な部分は「〜ということでよいですか？」と具体的に確認する
- 選択肢を出すときは**多くて4つまで**

---

## フェーズ1：何を作るか（concept.md のため）

### 聞く項目（重要度順）

| 優先 | 確認事項 |
|------|----------|
| 高 | 誰のためのアプリか（想定ユーザー） |
| 高 | そのユーザーのどんな困りごとを解決するか |
| 高 | 最初にリリースしたい最小スコープはどこまでか |
| 中 | 主要な画面・操作の流れ |
| 中 | 「これができたら成功」と言える条件 |
| 低 | 参考にしたい既存アプリ・サービス |

### アイデアが固まっていない場合

「何を作ればいいかわからない」と言われたら、**3ステップで絞り込む**。
一度に全案を並べず、1ステップごとに回答を受けてから次を出す。

**ステップ1 — 大まかな方向性を選んでもらう**

- 自分の作業を楽にするツール（効率化）
- 何かを練習・学習するためのアプリ
- 情報を集める・整理する・見せるアプリ
- その他（ゲーム・コミュニケーションなど）

**ステップ2 — 具体案を2〜3提示する**

選ばれた方向性に沿って、実現しやすい具体例を出す。
各案に「誰がうれしいか」と「作る難しさの目安（★☆☆〜★★★）」を添える。

**ステップ3 — 「一番の価値」を一緒に言語化する**

案が選ばれたら「このアプリを使った人が一番『助かった』と感じるのは
どの瞬間だと思いますか？」と聞き、核心を引き出す。

### フェーズ1完了の条件

以下が揃ったら `docs/concept.md` の草案を提示してよい。

1. 誰の何を解決するかが明確
2. 最小スコープが合意されている
3. 主要な画面・操作のイメージが共有されている

→ 承認を得てから `docs/concept.md` を作成する。

---

## フェーズ2：どう作るか（architecture.md のため）

`docs/concept.md` が承認されてから行う。フェーズ1で判明済みの内容は再度聞かない。

### 聞く項目（重要度順）

| 優先 | 質問 | 答えが左右する決定 |
|------|------|--------------------|
| 高 | どこで動かすか（ブラウザ / デスクトップ / スマホ / コマンドライン） | プラットフォーム・フレームワーク |
| 高 | データの保存は必要か。必要なら本人だけが見られればよいか | localStorage / DB / バックエンドの要否 |
| 高 | 複数人で同時に使う要素はあるか | サーバー・リアルタイム通信の要否 |
| 中 | 外部サービス（API・認証・決済）との連携はあるか | 依存ライブラリ・認証基盤 |
| 中 | スマホでも使えるようにしたいか | レスポンシブ対応の有無 |
| 低 | 開発言語の経験はあるか | TypeScript 導入可否・説明の量 |
| 低 | 使いたい技術・避けたい技術はあるか | 選定の自由度 |

### 技術選定の目安

| 条件 | 推奨スタック |
|------|------------|
| ブラウザで動く・シンプル・学習目的 | Vanilla JS / TypeScript + Vite |
| ブラウザで動く・画面数が多い・状態管理が複雑 | React or Svelte + TypeScript + Vite |
| デスクトップアプリにしたい | Electron or Tauri |
| コマンドラインツール | Node.js / Python（用途次第） |
| データ保存が本人のみ・少量 | localStorage / IndexedDB |
| データ保存が共有・大量 | SQLite → PostgreSQL（規模次第） |
| 複数人が同時に使う | 上記 + サーバー（Node.js / WebSocket） |

**迷ったら小さく始める。** 後から足せるものは最初から入れない。

### 提案の形式

```
## 提案アーキテクチャ

**メインスタック**: [選択したスタック]
**理由**: [ヒアリング結果に基づく根拠]
**却下した選択肢**: [代替案と却下理由]

### 構成要素
- フロントエンド: ...
- ビルドツール: ...（必要な場合のみ）
- データ永続化: ...（必要な場合のみ）
- サーバー: ...（必要な場合のみ）
- テスト: ...
```

→ 承認を得てから `docs/architecture.md` を作成する。
   重要な技術判断は `docs/decisions/` に ADR として残す。

## 完了後

2. `README.md` を更新する
3. 最初の作業メモ `work/YYYYMMDD-HHMM-タイトル/` を作成し、実装に入る
