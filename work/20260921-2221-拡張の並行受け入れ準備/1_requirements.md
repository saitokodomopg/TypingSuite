# 1. Requirements — 拡張の並行受け入れ準備

## 目的

「疎通確認」workで `core/` の判定エンジン・registry・練習画面が実際に画面から
動くことを確認できた。次の段階として、複数の生徒が `tasks/`（将来的には `games/`）を
分担して並行に拡張できる状態を整える。

現状は `PracticeScreen.tsx` が特定の1課題（`touch-type-fj`）を直接importして
固定表示しているだけで、複数の課題を同時に登録・切り替える動作は未検証。
生徒が着手する前に、ここを整えておく。

## やること

- `src/tasks/index.ts` を新設し、各課題モジュールの登録用importをここに集約する
  （`PracticeScreen.tsx` から個別課題への直接importを外す）
- `PracticeScreen` に簡易な課題切り替え（セレクトボックス程度でよい）を追加し、
  registryに登録された複数の課題を選んで試せるようにする
- ダミーの課題をもう1つ追加し、2件同時登録で衝突しないことを確認する
  （本番のコンテンツではなく、動作確認用の最小限のもの）
- `src/tasks/README.md` を作成し、以下の2部構成でまとめる
  1. **課題メニュー** — 生徒が選べる課題の候補ごとに、説明文・出題イメージ・
     完了の目安を書いた一覧。固定の候補を数多く用意しつつ、
     どれにも当てはまらない場合に自分でテーマを決められる
     「オリジナル課題」枠も設ける。これを読むだけでどれをやるか選べるようにする。
     **達成基準は共通で1つに統一する**：内容（○件以上）を用意したうえで、
     自分の作業ブランチをpushし、そこで自動発行される**プレビューURL**を
     ブラウザで開いて実際に動くことを確認できれば完成とする。
     mainへのマージは別工程（先生がまとめて取り込む）とし、生徒のゴールに含めない
  2. **追加の手順** — 選んだ課題を実装する具体的な手順
     （`docs/architecture.md` の「拡張の仕組み」を土台に、コピペで進められる
     テンプレコード付きでより具体的にする）。
     ブランチの切り方・pushの仕方・プレビューURLの見つけ方もコピペ用コマンドで示す
- `docs/backlog.md` の「次にやりたい」に、ゲーム側の候補一覧を追記する
  （タイムアタック／落ちてくる単語／RPG風／コンボスコア）。
  `Game` 型が未整備のため、今回は課題メニューには含めず候補として記録するのみ

## 受け入れ条件

- [x] ダミー課題を2件registryに登録しても衝突せず、両方とも動作する（テストで確認）
      → `src/tasks/index.test.ts`／Playwrightでの動作確認で検証
- [x] `PracticeScreen` の画面上で課題を切り替えて表示・プレイできる
- [x] `src/tasks/README.md` だけを読んで、他ファイルを探さずに新規課題を追加できる
      （生徒目線でのセルフチェック。既存の `touch-type` をテンプレとして示す）
- [x] 課題メニューの説明文だけを読んで、生徒が「どれを選ぶか」「何を作れば完了か」を
      自分で判断できる（先生や他の生徒に確認しなくてもよい粒度）
- [x] 「ブランチをpush→プレビューURLでブラウザ確認」が達成基準として明記されており、
      mainへのマージが生徒のゴールに含まれていないことが読んでわかる
- [x] `docs/backlog.md` に候補一覧が追記されている
- [x] `npm run test` / `npm run typecheck` / `npm run lint` がすべて通る
